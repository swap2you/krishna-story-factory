# 09 — Audio Verification, Stories 001–008 (DEF-06)

## Background

DEF-06 (audio playback failure) was open and release-blocking across V1.2, V1.3, and V1.4. Root cause established in prior UAT cycles: native `<audio>`-element-driven HTTP request issuance silently failed while `fetch()` to the identical URL succeeded, on certain routes/browsers.

## V1.5 fix architecture (verified live)

V1.5 ships a "blob-first" playback architecture:

1. On page load, the player prefetches the full narration MP3 as a `Blob`.
2. The player root element (`.audio-player`) exposes `data-playback-path`, observed to transition through states: `blob_ready` (prefetch complete, before Play is pressed) → `blob_playing` (after user gesture starts playback).
3. Before Play is even clicked, `audio.currentSrc` is already a genuine `blob:` URL and `audio.readyState === 4` (HAVE_ENOUGH_DATA) — confirming the blob is fully buffered ahead of interaction.
4. A native-MP3 fallback path exists for browsers where Blob playback is not viable (see WebKit note below); commit `fe57b46` ("fix(audio): fall back to native MP3 when blob playback is unsupported") is exactly this fallback.

## Live verification — all 8 released stories

For each of Stories 001–008, independently, in the live rendered app (Claude-in-Chrome, Chromium-based):

- `.audio-player[data-playback-path]` observed at `blob_ready` on load.
- Play button pressed → state transitioned to `blob_playing`.
- `audio.currentTime` observed to genuinely advance (not stuck at 0).
- `audio.paused` correctly toggled by Play/Pause.
- ±15s skip controls functioned and correctly clamped `currentTime`.
- No console errors during playback for any of the 8 stories.

**Result: PASS on all 8 stories (001–008).** DEF-06 is genuinely fixed for Chromium, independently reproduced (not merely trusted from prior Cursor/automated claims).

## Story 008 specific cross-check

`output/008_the-meeting-of-nanda-and-vasudeva/manifest.json` declares:

- `audio.duration_seconds: 350.8`
- `audio.bytes: 5612995`

Live-observed in browser: `duration: 350.736` (matches within floating-point/encoder rounding), and on-disk file size matches `audio.bytes` exactly. This independently confirms the served asset is the manifest-described file, not a stale or substituted one.

## Known, documented, and accepted gap: WebKit/Safari

The automated suite intentionally skips the "play advances currentTime" assertion specifically for the `webkit-mobile` Playwright project:

```
apps/web/e2e/v14-audio-all-stories.spec.ts
apps/web/e2e/v12-audio-routes.spec.ts
```

Skip reason recorded in source: `"iOS WebKit autoplay policy"`. This accounts for exactly the "10 skipped" tests in the official Playwright run (`docs/product/uat/v1.5/runs/20260724-181701-fe57b46/playwright.log`, tail: `10 skipped / 350 passed (6.6m)`).

This is a legitimate, intentionally documented skip tied to iOS WebKit's autoplay restrictions — not a silently-hidden failure. However:

- **This CoWork review's live browser testing tool (Claude-in-Chrome) is Chromium-based.** It cannot independently exercise real WebKit/Safari audio behavior.
- Therefore, genuine WebKit/Safari audio playback (as opposed to the documented, intentional test skip) is **not independently verified by this review**, and remains a coverage gap shared by both the automated suite and this manual review.
- Per mission guidance ("For Chromium/Firefox, Blob playback is acceptable. For WebKit, allowlisted native narration is acceptable."), the native-MP3 fallback exists specifically to address this — but its real-device behavior on WebKit was not independently observed this session.

## Verdict for this section

**PASS for Chromium (all 8 stories, blob-first path, live-verified).**
**Not independently verified: real WebKit/Safari native-fallback playback** (sandbox/tooling limitation — Claude-in-Chrome is Chromium-based). Recommend a manual Safari/iOS spot check before final production sign-off if WebKit users are a material share of the audience.
